# Custom release publication boundary (issue #135)

At baseline db9fb59a the inherited Docker release workflow responds to `core-*` tags and publishes to the upstream project's official registry names. The custom branch must not use that publication path. Each inherited job is restricted to the exact upstream repository identity; the workflow token defaults to contents:read and only the upstream publishing jobs request write permissions. A YAML-parsing architecture test checks the complete job list, repository guard and job permissions. This is a source guard, not a repository-wide settings change.

The clean fork main is intentionally untouched and still inherits the upstream workflow. Never push core-* tags from main or other unreviewed refs; no registry credentials for upstream should be configured in the fork. Review repository Actions permissions and tag protection separately. Custom release tags follow the MASTER convention, not core-*. A future custom release workflow must use separately approved destinations, least privilege, immutable tested source, and a human release gate. No actual tag, release, registry login or publication is performed here. Recheck the guard after every upstream integration. The unresolved upstream license/manifest discrepancy remains a distribution gate.
