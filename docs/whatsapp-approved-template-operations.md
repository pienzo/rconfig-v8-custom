# WhatsApp approved-template workflow (F03/F04)

Candidate, not authorized for activation. Reviewed 2026-11-24 against Meta's official [Business Messaging Policy](https://business.whatsapp.com/policy), [Cloud API overview](https://developers.facebook.com/documentation/business-messaging/whatsapp/overview/), [template reference](https://developers.facebook.com/docs/graph-api/reference/whats-app-business-hsm/) and [pricing](https://business.whatsapp.com/products/platform-pricing/).

Use a business account and registered sender, recipient opt-in and documented permission/opt-out handling. Obtain approval for the exact templates and locale with positional body parameters, normally Utility if Meta accepts that classification. Configure success/failure separately. Actual pricing depends on destination market/category and delivery; obtain account-specific approval before enabling. Do not assume free delivery or Direct Send eligibility. No WhatsApp Web automation.

The operator configures template names and ordered comma-separated fields from the allowlist: device.name, backup.status, backup.source, backup.timestamp, event.id. Blank mapping means no body parameters. Title and static body are authored/approved in Meta Business Manager; changing static text requires the provider workflow, not arbitrary free-form text from the local editor. Example for a three-parameter approved body: device.name,backup.status,event.id. Keep names and field values non-sensitive. No device IP, filename, config content, paths, credentials or raw error data in automatic mappings.

Both automatic global and WhatsApp flags plus explicit policy approval are required for automatic preflight. The preflight builds an immutable in-memory request and opaque HMAC destination; no external call until the closure is invoked. Provider acceptance is not delivery confirmation. The scheduled dispatch candidate adds the existing source activation floor plus RCONFIG_WHATSAPP_FROM_UTC (later of the two), an explicit policy gate, durable single-attempt claim and synthetic HTTP dispatch tests for native and external outcomes. Set a new approved cutoff on destination, key or template approval changes. Stop and restart workers with the approved configuration after withdrawal or changes; configuration is cached in long-running workers. Local mapping editor, real worker/recovery tests, actual approved-provider test and operational consent withdrawal review remain follow-up gates. Do not enable flags until all approved. Never put actual account credentials or recipient details in GitHub.
